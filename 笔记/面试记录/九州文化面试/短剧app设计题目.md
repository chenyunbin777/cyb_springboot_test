# 一、系统架构与设计（宏观与拆解）
## 如果让你设计一个海外短剧App的整体后端架构，你会怎么做？会用到哪些Java技术栈？
考察点：微服务划分、技术选型理由。
回答思路：不能只回答“用Spring Cloud”。要体现出业务拆分的思路。
可以将系统拆分为用户服务、内容管理服务（短剧元数据）、播放服务、推荐服务、搜索服务、支付/订阅服务、通知服务等。
技术栈方面，
基础框架用:Spring Boot，
微服务体系用:Spring Cloud Alibaba（Nacos做注册/配置中心，Gateway做网关），  Spring Boot + dubbo + zk/Nacos做注册中心
服务间调用用OpenFeign，
数据层用MySQL + MyBatis-Plus，
缓存用Redis，
消息队列用Kafka或RocketMQ


## 你会如何划分微服务？依据是什么？
拆分依据：根据监控系统的流量来拆分，**流量大**的可以拆分出单独的【微服务】，然后分布式部署保证【高可用性】
比如用户服务中：流量最大的服务接口应该就是登陆/注册，获取用户信息等。 
- 在用户量大的时候要保证服务的【高可用性】【稳定性】最好单独部署。既保证服务的质量（应该是最重要的服务，核心服务），也避免影响到其他的服务，导致其他服务【不可用】。

就好比秒杀系统设计一样。

并不是拆分系统越多越好：拆的越多，【可维护性】就越差！因为：服务治理的难度就越高之间的
 
如果开发人员太少的话，就很容易出错！

## 短视频上传和播放的完整链路是怎样的？
### 上传：客户端上传 → API网关鉴权 → 业务服务接收文件 → 上传至对象存储（OSS/MinIO）
### 播放：客户端请求播放 → 业务服务鉴权（判断VIP等） → 返回CDN的播放地址 → 客户端从CDN拉流播放，同时播放服务记录观看行为。

## 面对海外多语言环境，如何设计多语种内容管理与翻译工作流？
考察点：国际化（i18n）方案设计。

回答思路：可以设计一个内容本地化服务，负责管理不同地区的短剧标题、简介、字幕甚至配音版本。
翻译流程可以对接第三方翻译API（初译）加上人工审校（精译）。数据存储上，可以在内容表中通过language_code和region_code来区分不同版本。

## 短剧的搜索体验如何优化？
考察点：对Elasticsearch等搜索引擎的应用。
回答思路：引入Elasticsearch作为检索引擎。
优化点包括：建立合理的索引映射（支持多语言分词，如使用ik插件或对应的英文/小语种分词器）；
设计搜索建议（Suggestion） 和自动补全（Autocomplete） 功能；
优化搜索结果排序（结合热度、用户偏好等）

中文场景：优先用 IK Analyzer（兼顾易用性和效果），需拼音搜索则搭配 Pinyin Analyzer。
英文场景：通用用 Standard Analyzer，需词干提取用 English Analyzer。
日志/符号保留：用 Whitespace Analyzer 或 Pattern Analyzer（自定义分隔符）。
精确匹配整体：用 Keyword Analyzer（等价于 keyword 字段类型）。
前缀补全/模糊搜索：用 Edge Ngram Analyzer（前缀）或 ngram_analyzer（任意子串）。

## 如何设计一个支持三千万用户同时在线的短视频/短剧系统？

1、分布式部署，保证服务的高可用性，稳定性！根据不同的请求流量，增加对应的服务器来应对。
2、代码层面，尽量减少冗余逻辑，清晰、明了，要学会抽象与封装【相同的逻辑代码】/ 减少内存的消耗，不要用【大对象】一次性加载到内存，尽量拆分。
内存泄漏/内存溢出OOM ，JVM 对象的GC的监控，减少fullgc，要学会对【垃圾收集器】【内存】进行优化。
3、数据存储：mysql优化，索引优化，DB主从架构/读写分离。
4、缓存的使用：本地缓存+分布式Redis缓存架构，降低DB压力并且使查询更快、更高效。 单线程+多路复用模型/对于CPU不敏感，单redis qps 10w级别。
redis为什么快？一次内存访问约0.1微秒，而MYSQL磁盘随机IO需要10毫秒。

海外短剧App在数据存储和隐私方面需要注意什么？

考察点：对GDPR等海外法规的了解。

回答思路：需要遵守各地的数据保护法规（如欧盟GDPR、美国CCPA）。在架构上要考虑数据本地化（将欧洲用户数据存储在欧洲的服务器上），并提供数据导出和账户删除的功能接口




# 那这些核心功能一般都是单独部署的，不会跟其他的服务有影响，为什么还要降级

数据库（DB）、缓存（Redis）、消息队列（MQ）和网络带宽
连接池和CPU资源
防止“级联故障”和“线程池耗尽”

核心服务虽然在独立进程，但它通常依赖外部第三方（如支付网关、物流接口）

降级（如熔断）在此处的作用是：当检测到支付接口超时率达到【阈值】时，立即切断请求，快速返回“支付处理中，请稍后查询”，释放线程资源，保证系统还能接收新订单，而不是死等第三方。

同步请求改成异步处理 降低服务器压力

依赖链的“木桶效应”
核心业务往往由多个微服务编排而成（下单 -> 扣库存 -> 扣积分 -> 发券 -> 通知）。
