## 问题：是否存在过，一个订单多次支付的情况？ 要保证：幂等性
### 1、用户可能因为网络延迟双击“支付”，使用【业务幂等 + 分布式锁】支付接口使用Redis分布式锁，同时创建订单时写入【支付订单号】。
重复请求会加锁，并且会校验该订单是否已经支付过！

### 2、库存扣减逻辑
（1）先扣库存，再支付！ （一般处理方式） 
预占冻结 + 异步最终一致性。我们在下单生成订单时就预扣库存，支付环节仅做“确认扣减”操作，减少支付关键链路的资源锁竞争。
支付成功后，通过本地事务+消息队列（RocketMQ/RabbitMQ）异步通知财务模块生成结算凭证，确保业务库与财务账最终一致。

（2）或者是支付成功之后再扣库存
这里扣减库存，很有可能会有不成功的情况。 如果此时多用户【争夺库存资源】 要加锁，会有用户抢不到。这里还需要给用户退款的同时，修改订单状态为关闭。

（3）或许允许库存超扣的情况，后续再慢慢补充库存（相当于预售）

# 方案一：最佳实践 —— 同步实时验证（推荐）
在标准的 IAP 对接中，【不需要等待异步回调】。正确的做法是：客户端拿到凭证后，后端立即同步调用 Apple 的 App Store Server API 进行验证，并将结果直接返回给前端。

1、流程：客户端 purchase() 成功 -> 获取 JWS 凭证 -> 调用你自己的后端接口 /api/iap/verify -> 后端携带 .p8 密钥同步请求 Apple api.storekit.itunes.apple.com -> Apple 返回交易状态。

2、如何通知前端：后端的接口直接通过 HTTP 响应体（如 {"code":0, "data": {"valid": true}}）返回给前端。前端拿到响应后，立即展示“支付成功”并发放权益。

3、注意：在这个同步过程中，你依然要判断 status。如果 Apple 返回 PENDING（如家庭共享等待批准），你的接口应该返回“等待中”状态，前端轮询此接口，直到状态变为 PURCHASED 或超时。

还可以设置一个【超时时间】，5～10s还没有支付成功：需要提醒用户【“订单已提交，正在处理中，请耐心等待！” 或 “请稍后查看订单记录”】，然后允许用户【退出当前界面】去做其他事情。
然后转换成【监听支付消息通知】作为【数据补偿的方式】【兜底逻辑】。 
【回调接口逻辑】：首先判断订单状态是否已经是支付完成，如果是就不需要后续流程；支付未完成就可以进行后续【发货的流程】。

# 数据库优化
## 索引优化 查询优化：让SQL更高效
1、索引优化：联合索引（最左前缀原则） 索引覆盖：select a,b where a=x,b=y、索引下推：Using index condition，索引层面的过滤，而不是存储引擎层面，效率更高
2、查询方式优化：where or  ，表达式，like，null值判断
3、修复空间碎片：optimize table 表名; 定期重建或重组索引来消除碎片，可以维持其高性能
4、explain 分析查询索引使用方式

# 数据库架构设计
## 表结构设计
1、使用【字段冗余】的方式，减少关联查询
2、增加Redis缓存（热点数据、常用数据，不经常变化数据），降低DB压力。
3、Mysql读写分离。 主从架构模式，提高DB高可用性，以应对高并发的场景。
4、进行分库分表的方式，降低单库或者单表的压力。一般500w数据以上就可以考虑分表。
5、【同步双写】进行数据迁移到【新的分表中】。  

# 硬件与基础设施：提供底层动力
1、存储：优先使用SSD或NVMe硬盘，能极大提升数据读写速度。使用固态硬盘
2、网络与CPU：确保网络带宽充足，并根据并发量配置合理的CPU核心数。


# 监控与工具：知己知彼
1、利用监控看到自己的DB的性能的瓶颈在哪里？从而优化
2、比如、CPU使用情况、慢查询日志、内存等

# 配置参数调优：因地制宜

内存相关：如MySQL的innodb_buffer_pool_size，通常建议设置为物理内存的50%-70%。

I/O相关：对于I/O密集型业务，可调整预读策略等参数来提升性能。

优化器相关：可通过调整optimizer_prune_level等变量，控制查询优化器搜索最佳执行计划的“努力程度”。



# 总结
数据库优化是一个持续迭代的过程。建议遵循以下步骤：

1、监控与定位：利用工具找到真正的性能瓶颈。

2、从索引和查询入手：这是性价比最高的优化手段。

3、调整配置：根据业务特征精细化调整数据库参数。

4、优化架构：当【单点性能】达到极限时，考虑从架构层面进行改造。

5、持续迭代：业务和数据在变，优化工作也应持续进行

# Redis优化，缓存优化
## 缓存经典问题：防患于未然
1、缓存穿透（查不存在的数据）：缓存空对象或使用布隆过滤器 (Bloom Filter) 拦截。
2、缓存击穿（热点key失效）：设置互斥锁 (Mutex)，只让一个线程去重建缓存。
3、缓存雪崩（大量key同时失效）：设置随机过期时间。
